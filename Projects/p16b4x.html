a letter in the P column implies that instruction requires a specific privilege 
 a letter followed by '?' implies that instruction MAY require specific privilege, depending on operands
	see [PRIVILEGE_LEVEL]
Letter in E column identifies extension necessary to run the instruction
 a letter followed by '?' implies that instruction has extended functionality if an extension is present
	see [EXTENSIONS]

To fit this many instructions, encoding is more complex than in previous iterations and done in up to 3 stages.
AAAAACCC ___BBBBB
AAAAA is decoded first, most instructions it specifies have 8- or 11-bit immediate, exception to that being conditional moves. AAAAA = b00001 is reserved for software defined instructions, AAAAA = b00010 contains some privileged instrution, AAAAA = b00010 is reserved for miscelaneous. These instructions are chosen by CCC. When AAAAA = b00000 then first BBBBB is checked and then CCC. If BBBBB is 00000 then the instruction is invalid. This is to prevent uninitialized memory from being executable. If BBBBB is 00001 to 00011 or above 01000 then instruction is decoded. Otherwise, one more stage with CCC has to be decoded.

Most instructions have zero extended immediates. An exception to that are jumps and calls. Since jumps backward and forward are both often needed, jumps and calls have sign extended immediates. Also, to reduce the instruction count needed, jmp and cal have 11-bit immediate.

For all other cases, there is upper immediate mechanism. If an instruction is preceeded by XWR UI then 8 lower bits of UI replace upper 8 bits of immediate decoded from instruction. In particular, when jumps are preceeded by upper immediate write then upper 8 bits are replaced, even if original instruction had 11-bit immediate.

As was hinted, jumps are relative, making them absolute was significant mistake in previous project. This time it would have been even worse decision, as OS may put a program anywhere in memory. So, literally /*in literal defintion of the word*/, every single jump might need additional XWR making them effectively 32bits. Even though most jumps are really close!

OS SUPPORT

Supporting OS and multitasking requires privilege and virtual memory. /*well, not necessarily, see DOS, but it's safer this way*/.

PRIVILEGES

Privilege level is implemented with higher than typical granularity. Instead of 2 modes, each dangerous feature requires specific privilege. Notable example is IO access. Instead of letting all drivers access everything about processor, they can only use PWR and PRD. They are switched on INT, IRT, and CWR to specific register (x0002 or x0003, depends on privilege).

VIRTUAL MEMORY

Virtual memory is needed for process isolation without getting into the whole segmentation mess. Implementations can get quite complex with many levels of indirection, especially with larger address spaces. It is one of the things that gets much easier with 16-bit address width.

Here, there is a single layer of translation that turns upper virtual 5 bits into upper physical 10 bits - turning address into 21-bits. It is always on, on boot it is set up to map virtual addresses 1:1 (zero padded) to physical with full rwx permissions. Thanks to this:

  • stupidly simple programs /*tests*/ do not need to bother with VMem and do not require OS
  • VMem is always on, making HW just a bit simpler with less possible critical paths

Consequently, TLB must always support at least 1 full address space. For 16bits with 2kiW pages, that is just 32 pages, with 16-bits per translation, that is 512 bits, not nothing but not outrageous.
//TLB is partly architectural partly microarchitectural
//minimum requirements and interface are listed but specific structure and what is contained is implementation detail

Page Table is organized as 16 16-bit entries, it can be stored anywhere in 16-bit physical address space. Each entry has: present bit, protected bit, dirty bit, rwx bits, frame id. Note the lack of PID, hardware assumes that page table is for currently running process. Though it might cache different mappings for performance reasons. Therefore any change to page table always requires flush, other than new page addition, even if the process is not currently in use.

There is no need to support cached/uncached pages as IO is done fully through port instructions.

IO

IO is divided into two mechanisms: interrupts and ports. //I have DMA in plans, but not even a is ready sketch yet

INTERRUPTS

Interrupts may occur at different times but they are always presented before the new instruction starts. Sometimes they may stop the execution of current instruction when it causes fault, most notable example: page fault. OS has to set up interrupt handler table, which is 256 entry table of where the hardware must jump to on corresponding interrupt. This mapping is then loaded to internal buffer by the hardware and can be freely removed from memory.

From software point of view, port based IO behaves EXACTLY like memory. Data is read from or written to specific address. Behind the scenes, much more can happen, see system

SASM

Synthesizing ASseMbler

SASM is not a groundbreaking assembler. It must work reliably and be convienient to use. It also must work fast enough to never cause slowdown. Therefore SASM provides: instruction support /*no way*/, labels, expression system, preprocessing directives, macro system. //well, macro system is in the works... It is harder than I thought.

For simplicity, expressions use postfix format. All operators necessary for metaprogramming, label and bit manipulation are supported. There are 2 types of expressions: constant and non constant. The names are suboptimal, constant means that no label is used. Directives that influence code generation (eg %ADR) are required to use constant expressions. Otherwise it might not be possible to decide on binary layout. Since they use postfix, simple stack suffices to evaluate all expressions, which saves a ton of work.
For example {1 2 4 + -} evaluates to 2 + 4 - 1 = 5.

Directives are mostly used for metaprogramming with few dedicated for data placement. They turned out to be very useful for verification of correct instruction behavior. EXAMPLE

Internally, SASM performs few passes on the input.

  1. Input on the whole is converted into a bunch of tokens. Each token identifies basic construct (like string or number). There are three modes of parsing - regular, string, comment. String converts everything between " into singular string. Comment ignores everything from its start until end of the line.
  2. Syntax is verified, all structures are checked. I quite like the solution to verification and codegen, see below.
  3. Most directives are evaluated and all labels are collected. This step could be merged with previous one but is much simpler when they are separate.
  4. All remaining directives are evaluated here and everything is turned into actual code.
  5. There are few output modes possible depending on the need - e.g. VHDL output so output can be pasted directly into memory code.

The solution I mentioned above is:

Tests cover each stage of processing, making sure that no invalid case passes through.

First, each proper construct is tested to check whether they get turned into accurate lexems. Bunch of invalid tokens are checked whether they are properly reported. One test group includes randomly generated /*some time ago, not each time*/ input to see whether SASM reports proper errors.

Then, All structures are verified. Each instruction and directive is checked, not exhaustively but enough to be quite sure of correct behavior. That means each variant is checked, but values are picked arbitrarily. /*Quite often I picked 0 as the value, oh well, not the brighest one around*/.

Then all preprocessing possibilities are verified, including few invalid kinds.

Finally, all codegen options are verified.

Performance tests are also in the works, though SASM works good enough so it is not a priority.

Error messages are unfortunately part of test system. looking for solutions!

DASM

Desynshesizing ASeMbler
not quite assembler

This is the simplest subproject.

2 modes are implemented

  • interactive (stdin)
  • file
Both call disassemble(uint16t) which prints actual disassembly.

There is no global state that influences instruction formats so disassembly is trivial. First, decode all possible operands (unused will be ignored). Then switch based on opcode.

I do not think there is generally faster solution, happy to be proven wrong.

COSI

Currently, simulator is quite barebones but is mostly complete. Old iteration was more interesting but required change to properly integrate IO and specialization for microarchitectures.
//Most of the stuff will be reimplemented here once the basic FPGA implementation is done

Simulator operates in a loop

  1. Print basic debug info
  2. Execute instruction
  3. Check instruction side effects
  4. Check interrupts
  5. Check breakpoints and debug commands
At the end, it might print some more debug info.

Instruction is chosen almost exactly in the same fashion as in DASM URL. And the path diverges into more files. This also provides quite convenient way to switch implementation that is used. To change microarchitecture, replace instruction.* files. Other than microarchitectures, this can /*and will*/ be used to implement ultra fast simulator with minimal error checking and very careful simulator with extensive error checking. This implementation is inbetween, not too fast, not too safe.

All instructions are simple so each case is simple too. Often there are checks for interrupts.

memory.* has quite long check for various translation errors. This I suspect to be bottleneck in the future so it would be good to somehow skip most of it.

Interrupts are global state that is rised by various events. As they are presented as synchronous, it does not actually matter whether they are checked or generated asynchronously. Though it does mean that some interrupts like timer need to be implemented with special care. Not implemented here, but simulator is generally fast enough and timer slow enough to make ocasional check with std::chrono good enough.

IO is somewhat synchronous, in that it communicates via synchronous instructions. /*DMA would make that not true*/ So it is implemented as deep switch for each io::read and io::write possibility. So also, to change the system the CPU is integrated into, changing io.* is sufficient.

To be impplemented is various performance measurement systems, some TUI debugger, and ultra fast implementation.

Attentious reader might notice lack of tests, they are shared with the CPU and thus covered in tests section URL .
